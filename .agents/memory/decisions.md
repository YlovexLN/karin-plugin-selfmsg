# 架构决策记录

每条记一件事：**当时有哪些选项、为什么选了这个、付出了什么代价**。
想推翻某个设计之前，先读对应条目——大概率当初已经权衡过。

---

## ADR-1 在 `emit` 层改写，而不是注册命令

**背景**：目标是让 kkk 处理另一个框架发出的链接。

**选项**

| 方案 | 结果 |
| --- | --- |
| 用 `karin.command` 监听链接 | 收不到，事件在适配器层就被丢弃 |
| 用 `karin.accept` 监听自定义事件 | 同上，`message_sent` 不是已注册类型 |
| 请求框架提供 hook | 没有这个扩展点，且远水不解近渴 |
| 运行时接管 OneBot 客户端的 `emit` | 可行 |

**决定**：接管 `emit`，把事件改写成标准 `message` 后原样交回框架分发器。

**代价**：依赖 `bot._onebot` 这个未文档化字段，框架大版本升级可能失效；
失效表现明确（`没有找到 _onebot，接管失败`），可快速定位。

## ADR-2 不改 node_modules 里的适配器源码

**背景**：最直接的办法是改 `adapter/onebot/core/core.ts` 的 `init()`，加一行分发。

**决定**：不这么做，改用插件形式。

**理由**：Docker 部署的 Karin 每次更新镜像都会覆盖 `node_modules`，改动必然丢失，且用户
不会意识到"更新后为什么不工作了"。插件目录是用户自己的数据，不会被镜像覆盖。

**代价**：要维护一套与框架内部实现耦合的代码。这个代价由插件承担，而不是由用户承担。

## ADR-3 私聊伪造 `user_id` 为对话方

**背景**：`message_sent` 的 `user_id` 是 bot 自己。

**选项**

| 方案 | 结果 |
| --- | --- |
| 保持 `user_id` = bot | kkk 等插件普遍有 `user_id === self_id` 过滤，永远不触发 |
| 改成对话方 `target_id` | 能进入插件层 |

**决定**：改成 `target_id`。

**代价**：消息在框架看来不再"来自自己"。这意味着 Karin 侧插件的"忽略自发消息"保护失效，
控制点必须放在发送侧（即本插件的白名单）。这是刻意接受的取舍：如果不改，插件根本不工作。

## ADR-4 群消息伪造一个成员身份

**背景**：群内自发消息只有 `group_id` 和 `user_id`（= bot），没有"谁发的"。

**决定**：用 `groupSender` 伪造成一个成员身份（默认 `10000`）。

**代价**：

- kkk 的解析统计会记到这个号上；但不要填主人 / 管理员，会命中权限判断 → 默认 10000；
- 群里看到的是"某成员发了链接"，但卡片本身仍是 bot 发出，用户感知无差异。

**替代方案**：默认关闭群聊处理。曾作为默认值，后因实际需求改为默认开启。

## ADR-5 运行时状态挂在 `globalThis`

**背景**：Karin 支持热重载，改文件后模块会被重新求值。

**选项**

| 方案 | 结果 |
| --- | --- |
| 模块级 `WeakSet` / 变量 | 重载后重置，`emit` 被重复包装 |
| `globalThis` + `Symbol.for` | 跨模块实例共享，幂等 |

**决定**：`globalThis[Symbol.for('karin-plugin-selfmsg:state')]`。

**额外收益**：`apps/status.js` 与 `index.js` 在重载后可能是不同模块实例，共享同一份状态
才能让统计数字正确。

## ADR-6 配置只留文件一个来源（曾经历三版）

**背景**：配置该放在哪、允许几层覆盖。

**演进**

| 版本 | 方案 | 结果 |
| --- | --- | --- |
| 早期 | 只支持环境变量 | 改配置要进 compose 重启，WebUI 面板无从下手 |
| 中期 | 环境变量 > WebUI > 默认值 | 能用了，但出现了新的困惑源 |
| **当前** | **只有文件** | 当前方案 |

**为什么推翻中间那版**：三层优先级本身没问题，问题是**用户看不见自己在哪一层**。
配置文件里写死 `enable=false`、面板里点开是 `true`，实际行为跟面板不一致，而日志里当时
只有一句「配置来源」，说不清具体是哪个键被谁覆盖。修这一层要付出的解释成本，超过了
它带来的那点灵活性。

**决定**：`@karinjs/<包名>/config/config.json` 是唯一来源，包内 `config/default.json`
负责首次生成，WebUI 与手工编辑写的是同一个文件。不读任何环境变量。

**代价**：

- 纯声明式配置管理（在启动脚本里统一写死所有配置）不再可行，改配置必须动文件；
- 但换来的是"配置在哪一目了然"，以及删掉文件即可恢复默认值的逃生通道。

## ADR-7 多链接拆成多条投递

**背景**：一条消息里可能有两三个链接。

**事实**：kkk 的 B站正则一次只匹配第一个链接，实测两个链接只出一张卡。

**决定**：在投递前拆成 N 条，每条只含一个链接，间隔 1.5 秒。

**代价**：N 个链接会产生 N 次渲染，对 puppeteer 有压力；间隔可配置。
另外拆分出来的后续事件必须走 `rawEmit`，否则会被自己的静默窗口吃掉（见 I3）。

## ADR-8 包名带 scope，与「必须以 karin-plugin- 开头」有出入

**背景**：插件规范要求插件包名以 `karin-plugin-` 为前缀；而 GitHub Packages 强制要求
包名写成 `@<仓库所有者>/<名字>`，两者不能同时满足。

**决定**：取 `@ylovexln/karin-plugin-selfmsg`，前缀保留在 scope 之后。

**为什么不改回无 scope**：GitHub Packages 的 npm 源只接受 scoped 包名，无 scope 根本推不上去。
若改发 npmjs.org 公共源，可以回到 `karin-plugin-selfmsg` 干净名字。

**风险评估**：Karin 加载 npm 插件时，`node_modules/@ylovexln/karin-plugin-selfmsg` 的**末级目录名**
仍然以 `karin-plugin-` 开头，常见的目录名判断不会失效；但若有版本按完整包名做前缀校验，可能识别失败。
`package.md` 里写的是「npm 包则没有限制」，`standard.md` 里写的是「强制」，两份官方文档本身不一致。

**兜底**：如果实测加载失败，最稳的做法是让用户按「方式一」把目录直接放进 `plugins/`。
